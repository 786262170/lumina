## 🏗️ 一、项目整体架构设计

### 1.1 架构模式

项目采用 **MVVM (Model-View-ViewModel)** 架构模式，结合 **服务层模式 (Service Layer Pattern)**：

```
┌─────────────────────────────────────────────────────────┐
│                      View Layer                          │
│  (Pages: Splash, Login, Index, Workbench, etc.)         │
└────────────────────┬────────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────────┐
│                  Service Layer                          │
│  (RouterService, ApiClient, UserService, etc.)          │
└────────────────────┬────────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────────┐
│                    Model Layer                           │
│  (Types, Interfaces, Data Models)                       │
└─────────────────────────────────────────────────────────┘
```

### 1.3 设计原则

1. **单一职责原则 (SRP)**: 每个服务类只负责一个业务领域
2. **依赖注入 (DI)**: 使用单例模式提供服务实例
3. **关注点分离**: UI层、业务逻辑层、数据层清晰分离
4. **统一设计系统**: 所有UI组件使用统一的设计系统常量
5. **统一路由管理**: 所有路由跳转通过 RouterService 统一管理

### 1.4 服务层设计

#### 1.4.1 服务层架构

所有服务采用 **单例模式 (Singleton Pattern)**，确保全局唯一实例：

```typescript
class ServiceName {
  private static instance: ServiceName;
  
  private constructor() {}
  
  public static getInstance(): ServiceName {
    if (!ServiceName.instance) {
      ServiceName.instance = new ServiceName();
    }
    return ServiceName.instance;
  }
}
```

#### 1.4.2 服务列表（12个服务）

**核心服务**:
- `RouterService.ets`: 路由管理服务
- `ApiClient.ets`: HTTP请求客户端
- `UserService.ets`: 用户状态管理

**业务服务**:
- `AuthService.ets`: 认证服务
- `AIService.ets`: AI服务
- `ImageService.ets`: 图片处理服务
- `WorkService.ets`: 作品管理服务
- `SceneService.ets`: 场景服务
- `SubscriptionService.ets`: 订阅服务
- `SettingsService.ets`: 设置服务
- `UserApiService.ets`: 用户API服务
- `LoginService.ets`: 登录服务（Mock，仅用于开发测试）

**服务依赖关系**:
```
ApiClient (基础服务)
    ├── UserService (用户状态)
    │
    ├── AuthService
    │   └── UserService
    │
    ├── AIService
    ├── ImageService
    ├── WorkService
    ├── SceneService
    ├── SubscriptionService
    ├── SettingsService
    └── UserApiService

RouterService (独立服务，不依赖其他服务)
LoginService (Mock服务，仅依赖UserService)
```

> 详细的服务功能说明请参考 [六、文件功能说明 - 6.2 服务文件说明](#62-服务文件说明)

### 1.5 设计系统

项目使用统一的设计系统，所有设计常量定义在 `common/DesignSystem.ets`。

**设计系统包含**:
- **颜色系统** (LuminaColors): 主色、背景色、文字色、状态色、边框色
- **间距系统** (LuminaSpacing): XS(4px) ~ XXL(48px)
- **圆角系统** (LuminaRadius): SM(4px) ~ XXXL(32px)
- **字体系统** (LuminaTypography): 字号(DISPLAY_LG ~ LABEL)和字重
- **阴影系统** (LuminaShadows): 卡片阴影、按钮阴影
- **渐变系统** (LuminaGradients): AURORA渐变、图标背景渐变
- **尺寸系统** (LuminaSizes): 图标尺寸、按钮尺寸、导航栏尺寸、卡片尺寸

> 详细的设计系统说明请参考 [六、文件功能说明 - 6.4 配置文件说明](#64-配置文件说明)

## 📱 二、页面设计思路

### 2.1 启动流程页面

#### 2.1.1 Splash.ets (启动页)

**设计思路**:
- 应用启动时的第一屏，展示品牌形象
- 使用渐变背景和Logo动画提升视觉体验
- 自动跳转到欢迎页或登录页

**交互逻辑**:
```
启动应用
  ↓
显示Splash页面（2秒）
  ↓
检查登录状态
  ↓
已登录 → 跳转到Index
未登录 → 跳转到Welcome
```

**核心功能**:
- ✅ Canvas绘制Lumina Logo（太阳/女神图标，8条长射线+4条短射线+三层中心圆圈）
- ✅ 渐变背景（#667eea → #764ba2）
- ✅ 加载动画（旋转圆圈）
- ✅ 版本号显示
- ✅ 淡入动画效果

**技术要点**:
- 使用 `CanvasRenderingContext2D` 绘制Logo
- 使用 `LinearGradient` 实现渐变背景
- 使用 `setTimeout` 控制跳转时机

#### 2.1.3 Login.ets (登录页)

**设计思路**:
- 手机号+验证码登录
- 完整的表单验证和错误提示
- 支持微信快捷登录（预留）
- 支持游客模式

**交互逻辑**:
```
显示登录页
  ↓
用户输入手机号
  ↓
点击"获取验证码"
  ↓
验证码发送成功（60秒倒计时）
  ↓
用户输入验证码
  ↓
点击"登录"
  ↓
验证表单
  ↓
调用登录API
  ↓
登录成功
  ↓
判断是否新用户
  ↓
新用户 → 跳转到AIQuestionnaire
老用户 → 跳转到Index
```

**核心功能**:
- ✅ 手机号验证（11位，1开头，3-9第二位）
- ✅ 验证码验证（6位数字）
- ✅ 实时表单验证
- ✅ 验证码倒计时（60秒）
- ✅ 错误提示（手机号错误、验证码错误）
- ✅ 加载状态显示
- ✅ 自动登录检查（已登录直接跳转）

**技术要点**:
- 使用 `@State` 管理表单状态
- 使用正则表达式验证手机号和验证码
- 使用 `setInterval` 实现倒计时
- 使用 `AuthService` 处理登录逻辑
- 使用 `UserService` 保存用户信息

**表单验证规则**:
```typescript
手机号验证:
- 不能为空
- 必须为11位
- 必须以1开头，第二位为3-9

验证码验证:
- 不能为空
- 必须为6位
- 必须为数字
```

### 5.3 API调用难点

#### 5.3.1 难点描述

**问题**: HarmonyOS的HTTP API与Web不同，需要统一封装。

**挑战**:
- HTTP请求的封装
- Token的自动添加
- 错误处理（401/403/404等）
- 请求/响应拦截

#### 5.3.2 解决方案

**方案**: 创建ApiClient统一封装HTTP请求

**实现要点**:
1. **统一接口**: 提供get/post/put/delete方法
2. **自动认证**: 自动从UserService获取Token并添加到请求头
3. **错误处理**: 统一处理HTTP状态码，401自动清除Token
4. **超时控制**: 设置合理的超时时间（30秒）
5. **日志记录**: 记录请求和响应日志，便于调试

**关键代码**:
```typescript
export class ApiClient {
  async request<T>(options: RequestOptions): Promise<T> {
    // 添加认证头
    if (needAuth) {
      const token = await this.userService.getToken();
      if (token) {
        requestHeaders['Authorization'] = `Bearer ${token}`;
      }
    }
    // 处理错误
    if (responseCode === 401) {
      await this.userService.logout();
      throw new Error('登录已过期，请重新登录');
    }
  }
}
```

**效果**: API调用统一、简洁，错误处理完善，Token管理自动化。

### 5.4 图片处理难点

#### 5.4.1 难点描述

**问题**: 图片上传、处理、下载等功能在HarmonyOS中的实现方式与Web不同。

**挑战**:
- 文件上传（multipart/form-data）
- 图片处理进度查询（轮询机制）
- 大图片的内存管理
- 图片缓存策略

#### 5.4.2 解决方案

**方案**: 使用ImageService封装图片相关操作，使用轮询机制查询处理进度

**实现要点**:
1. **文件上传**: 当前使用模拟数据，后续实现multipart/form-data上传
2. **进度查询**: 使用轮询机制（waitForProcessResult）查询处理状态
3. **内存优化**: 使用缩略图减少内存占用
4. **异步处理**: 图片处理是异步的，返回taskId用于查询状态

**关键代码**:
```typescript
async waitForProcessResult(
  taskId: string,
  onProgress?: (progress: number) => void,
  maxWaitTime: number = 30000
): Promise<ProcessResultResponse> {
  // 轮询查询处理状态
  const checkStatus = async () => {
    const status = await this.getProcessStatus(taskId);
    if (status.status === 'completed') {
      return await this.getProcessResult(taskId);
    } else {
      setTimeout(checkStatus, 1000);
    }
  };
}
```

**效果**: 图片处理流程清晰，支持进度回调，用户体验良好。

## 🔒 附录H、安全设计

### 11.1 认证安全

**Token管理**:
- Token存储在本地Preferences中，使用系统级加密存储
- Token通过HTTPS传输（生产环境）
- Token过期自动清除，引导用户重新登录

**认证流程**:
1. 用户登录成功后获取Token
2. Token保存到UserService（本地存储）
3. 每次API请求自动添加Token到Authorization头
4. Token过期（401错误）自动清除并跳转登录页

### 11.2 数据传输安全

**HTTPS通信**:
- 生产环境使用HTTPS（`https://api.lumina.ai/v1`）
- 开发环境可使用HTTP（仅用于开发测试）
- 所有敏感数据（Token、用户信息）通过加密通道传输

**数据验证**:
- 客户端对用户输入进行验证（手机号格式、验证码格式等）
- 服务器端进行二次验证
- 防止SQL注入、XSS等攻击（服务器端处理）

### 11.3 本地存储安全

**存储方式**:
- 使用HarmonyOS系统提供的Preferences API
- 数据存储在应用沙箱中，其他应用无法访问
- 系统级加密保护

**存储内容**:
- 用户信息（加密存储）
- Token（加密存储）
- 登录状态（布尔值）

**不存储的内容**:
- 密码（使用验证码登录，无需存储密码）
- 支付信息（不本地存储）
- 敏感业务数据（优先服务器存储）

### 11.4 权限管理

**所需权限**:
- `ohos.permission.INTERNET`: 网络访问权限（必需）
- 其他权限按需申请

**权限申请原则**:
- 最小权限原则
- 明确说明权限用途
- 运行时动态申请（如需要）

## 🎯 附录O、关键设计决策

### 16.1 架构选择

**为什么选择MVVM + 服务层模式？**
- MVVM模式适合ArkUI的声明式UI
- 服务层模式便于业务逻辑复用
- 单一职责，易于维护和测试

### 16.2 路由管理

**为什么使用RouterService统一管理？**
- 集中管理路由逻辑，便于维护
- 统一处理路由参数
- 便于实现路由拦截和权限控制

### 16.3 状态管理

**为什么使用服务层而不是状态管理库？**
- HarmonyOS生态中状态管理库不成熟
- 服务层单例模式简单有效
- 减少外部依赖

### 16.4 设计系统

**为什么使用DesignSystem常量？**
- 统一设计规范，保持UI一致性
- 便于主题切换和样式调整
- 提高开发效率
